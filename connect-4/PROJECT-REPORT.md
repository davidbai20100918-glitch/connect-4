## 一、一句话总结

你原来的网站是"只能看、不能存东西"的静态网页。我们给它配了一个**云端小后端**（Cloudflare Worker）和一本**云端登记本**（D1 数据库），再接上 **Google 的身份系统**，于是访客可以用 Google 账号证明"我是谁"，然后留言。

游戏本身的代码一行没动，你的网址也没变。

## 三、为什么不能直接在原来的网站上做登录

这是整件事的起点，也是最重要的一个概念。

**GitHub Pages 只会"发文件"，不会"跑程序"。**

打个比方：你的网站目前像一台**自动售货机**——投币、出货，全按事先摆好的方式来。但登录需要"有人看着门口检查证件"，售货机做不到。任何"检查"逻辑如果只写在网页里（JavaScript），访客都能打开开发者工具改掉它。

> 真实风险：如果前端自己判断"这个邮箱看起来是管理员"，那任何人按 F12 改一行就能变成管理员。所以**凡是要"信"的东西，必须放在访客改不到的地方**——服务器上。

于是有了"前端 + 后端"的分工：

- 前端（浏览器里）：负责好看、好用、发起请求
- 后端（服务器上）：负责验身份、读数据、写数据。**这里说行才算行。**

## 四、过程时间线：做了什么，撞了什么墙，学到什么

### 阶段 1｜定方案（最初想错了）

一开始我按"把站点搬到 Cloudflare Pages"来设计，因为那样前后端同源，最省事。

**转变**：你已经有了 `github.io` 的网址，而且已经分享出去了。搬家 = 换网址 = 别人收藏的链接失效。所以我改成**保留 GitHub Pages，另外单独部署一个后端**。

> **教训**：技术方案要服从"用户已经拥有的东西"。能让现有资产不失效的方案，通常优于"理论上更优雅"的方案。

### 阶段 2｜Cookie 不能用，改用 Bearer 令牌

最初设计是"登录后发一个 Cookie"。很快发现不行：

- 页面在 `github.io`，后端在 `workers.dev`，这是**两个不同的网站**（不同"源"）。
- 这种跨站 Cookie 叫**第三方 Cookie**，Safari 和 Firefox 默认直接拦截。

**转变**：改成**令牌（Token）**方式。登录成功后，后端把一串"临时通行证"直接交给网页，网页存在 `localStorage` 里，每次请求把它放在 HTTP 头 `Authorization: Bearer xxx` 里带上。

> 比方：Cookie 是保安把门禁卡塞进你包里（你拿不出来，但跨小区不认）；Token 是你自己揣兜里的纸条（哪个小区都认，但被小偷偷到就麻烦）。所以纸条要设 7 天过期。

### 阶段 3｜写代码 + 自己做一次"假 Google"来测试

后端写完后不能直接上线赌运气。我写了一套本地测试：**自己生成一对密钥，冒充 Google 的签名服务器**，伪造各种"身份证"去撞后端。

测试里包括了几种真实攻击：

| 测试 | 模拟的攻击 | 结果 |
| --- | --- | --- |
| `alg: none` | 攻击者把算法改成"不用签名" | 拒绝 ✅ |
| 换了 `aud` | 拿别人家网站的合法 token 来用 | 拒绝 ✅ |
| 改签名 | 手动篡改 token 内容 | 拒绝 ✅ |
| 过期 token | 用昨天的旧 token | 拒绝 ✅ |

第一轮测试里真抓到一个 bug：未验证邮箱的账号应该返回 `403`（"你身份没问题但账号不能用"），我写成了 `401`（"你身份不对"）。改掉，重新跑通 14 项。

> **教训**：能自动跑的测试，比"我觉得应该没问题"值钱一百倍。

### 阶段 4｜发现你机器上没有 Node，于是把依赖删光

准备部署时发现这台电脑没装 Node.js/npm。而 `wrangler`（Cloudflare 的命令行工具）本身要 Node 才能跑。

**转变**：我原本用了第三方库 `jose` 来验签，改成**用浏览器和 Workers 内置的 WebCrypto 手写**。代价是多写约 80 行；收益是整个后端变成**零依赖**——意味着可以直接粘贴到 Cloudflare 网页控制台里运行，不需要任何工具链。

> **教训**："少一个依赖"往往比"少写几行代码"更值钱，因为依赖会带来安装、版本、网络三类失败。

### 阶段 5｜装 wrangler，被 pnpm 拦了一次

装是装上了，但 `esbuild` 和 `workerd` 的"安装脚本"被 pnpm 默认拦掉（新版 pnpm 出于供应链安全考虑，默认不执行依赖包的安装脚本）。

我先在 `package.json` 里写配置——没生效，因为 pnpm 11 把配置搬到了 `pnpm-workspace.yaml`。改对位置后，打包验证通过。

> **教训**：报错说"被忽略"时，先看它让你去哪儿改，别猜。

### 阶段 6｜OAuth 登录连挂三次

这是最折腾的一段。`wrangler login` 会让你在浏览器里点"允许"，然后回调到你电脑上的 `localhost:8976`。

| 尝试 | 现象 | 真正原因 |
| --- | --- | --- |
| 1 | `Timed out waiting for authorization code` | 你从看到消息到点"允许"超过 3 分钟，临时服务已退出 |
| 2 | `Gave up waiting... UND_ERR_SOCKET` | 这台机器到 Cloudflare 的网络时断时续 |
| 3 | `query string parameter doesn't match` | 你点的是**上一个**标签页，带回的是旧的 `state` 参数 |

三次之后我判断：这条链路对"人不在键盘前 + 网络抖动"太不友好。

> **教训**：一个反复失败的方案，往往不是"再试一次就好"，而是**设计不适应环境**。该换路子就换。

### 阶段 7｜改用 API Token

改成在网页上创建一个**API Token**（一串有权限范围的密钥），我把它放在环境变量里，`wrangler` 直接读取。没有时间窗口、没有回调、断了可以重试。

第一次还是失败：`Authentication error [code: 10000]`。我做了权限探测，发现：

```
200  Workers list      OK
200  Account details   OK
401  D1 list           ← 唯独没有 D1
```

也就是说这个 token 能管 Worker，但碰不到数据库。你在后台给这个 token 补了一条 `Account / D1 / Edit` 就好——**编辑已有 token 的权限不会改变 token 的值**，所以不用重新复制。

> **教训**：报错只说"认证失败"时，用一个最小请求去逐个试探权限，能精确定位缺哪一块。

### 阶段 8｜建库、建表、部署

- 建数据库 `connect4-comments`，落在**香港机房**（`region APAC`）
- 执行建表 SQL，得到两张表：`users`（用户）和 `comments`（评论）
- 部署 Worker，第一次失败：账号还没注册 `workers.dev` 子域
- 通过 API 注册子域 `davidbai20100918`，再部署成功

### 阶段 9｜HTTPS 打不开，做了一次"对照实验"

部署成功但 HTTPS 打不开，报 `SSL alert 40`。当时有两种可能：**网络封锁**，或者**证书还没签发**。

我没有猜，而是做对照实验：

| 测试 | 结果 | 说明 |
| --- | --- | --- |
| `https://1.1.1.1` | 301 ✅ | 到 Cloudflare 的网络本身通 |
| `https://cloudflare.com` | 301 ✅ | 同上 |
| `https://workers.dev` | 301 ✅ | 整个 `workers.dev` 域没被封 |
| `https://你的子域` | 握手失败 ❌ | **只有你这一个新子域不行** |
| `http://你的子域`（80 端口） | 200 ✅ | 服务活着，只是证书没就绪 |

四个控制变量一排除，结论唯一：**新子域的证书还在签发**。等了约 20 分钟再测，200 通过。

> **教训**：这叫**控制变量法**。与其猜，不如设计一个"如果 A 成立就应该是 X，如果 B 成立就应该是 Y"的实验。

### 阶段 10｜Google 那边也不一样了

Google 在 2026 年初把 OAuth 界面从"APIs & Services"拆成了独立的 **Google Auth Platform**，旧教程里的菜单已经没了。现在的入口是 `/auth/overview`、`/auth/audience`、`/auth/clients`。

另外还遇到两个小坎：

1. 要填"隐私政策链接"和"服务条款链接" → 我给你写了 `privacy.html` 和 `terms.html`，内容照着实际收集的数据写，你上传后两个页面都是 200。
2. 你第一次贴的是 `terms.html` 的网址而不是 Client ID → Client ID 的固定长相是 **`数字-一串字母.apps.googleusercontent.com`**。

### 阶段 11｜收尾 + 一次真实验证

Client ID 写进 Worker（`GOOGLE_CLIENT_ID`）和前端后，我用 `wrangler tail` 实时抓后端日志，发了一个"签名是假的"的 token 进去，日志出现：

```
"google token rejected: unknown signing key"
```

它能报"这个签名密钥我不认识"，说明**它真的去 Google 拉到了公钥列表、解析了 token、查了密钥编号，只是没找到对应的那把**。这证明 Google 验签链路是通的，只等真人来签。

### 阶段 12｜你提新需求：删除评论

加上了 `DELETE /comments/:id`，并且 SQL 里带了 `AND user_sub = ?`——**别人的 id 猜到了也删不掉**。测试从 14 项加到 18 项，全部通过，已重新部署。

## 六、名词表（按重要程度排）

### 身份与安全

**OAuth 2.0**：让你"用别人的账号登录"的行业标准。你从不在本站输入 Google 密码，全程在 Google 页面上完成。

**ID Token（身份证）**：Google 登录成功后发给前端的字符串，里面写着"这个人是谁、发给哪个网站、什么时候过期"，并附带一个**签名**。

**JWT**：ID Token 的具体格式，长得像 `xxxxx.yyyyy.zzzzz` 三段，分别是**头部.内容.签名**。内容只是 Base64 编码，**不是加密**——任何人都能解码看。所以它的可信度**全部来自签名**。

**签名 / 公私钥**：Google 用**私钥**盖一个"章"，全世界都能用它的**公钥**验这个章。私钥只有 Google 有，所以别人伪造不了。

**JWKS**：Google 公布公钥的网址，`googleapis.com/oauth2/v3/certs`。公钥会定期轮换，所以后端要按"密钥编号 `kid`"去找。

**aud（audience）**：这份 token 是**发给哪个网站**的。少了这项检查，别人家网站拿到的合法 token 也能登录你的站。**这是最容易被漏掉的一步。**

**iss / exp**：签发者是谁 / 什么时候过期。

**会话令牌（Session Token）**：验完 Google 的身份证后，你的后端自己发的"临时出入证"，7 天有效。它和后端共享一个密钥 `SESSION_SECRET`，所以后端能识别自己的证。

**Bearer Token**：把令牌放在请求头 `Authorization: Bearer xxx` 里的标准写法。"Bearer"= "持有者"，暗含"谁拿着就认谁"——所以必须走 HTTPS。

**localStorage**：浏览器里的一个小仓库。方便，但能被页面上的恶意脚本读到，所以叫"XSS 的靶子"。

**HttpOnly Cookie**：另一种存法，JavaScript 读不到，更安全。但因为跨站问题这次没用上。

### 网络

**DNS**：把域名翻译成 IP 地址的电话簿。

**HTTPS / TLS**：加密的 HTTP。握手时会验证"对方证书是不是真的"。

**证书**：由证书机构签发的"网站身份证"。Cloudflare 给 `*.workers.dev` 自动签发，新子域要等几分钟。

**SNI**：TLS 握手时浏览器会先说明"我要访问哪个域名"，这个词就藏在 SNI 里。某些网络封锁就是靠它识别并掐断的——这也是我一开始怀疑的方向。

**同源策略**：浏览器的安全规则。`a.com` 的页面默认不许随便读 `b.com` 的数据。

**CORS**：同源策略的"白名单机制"。后端必须主动回答"我允许 `github.io` 来访问我"，浏览器才放行。

**预检（Preflight）**：跨站发复杂请求前，浏览器先用 `OPTIONS` 问一句"我能发吗"。后端必须正确回答，否则请求根本发不出去。

### 云服务

**Serverless / Worker**：不用自己买服务器，传一段代码上去，Cloudflare 在全球几百个机房按需运行。

**D1**：Cloudflare 的 SQL 数据库，跟着 Worker 配套。

**绑定（Binding）**：把数据库"接"到 Worker 上，代码里就能用 `env.DB` 访问。只声明名字没用，必须真的绑上。

**变量 vs 密钥**：普通变量明文可见（如 `ALLOWED_ORIGINS`）；密钥（如 `SESSION_SECRET`）加密存储，后台也不显示。

**子域（subdomain）**：`你的名字.workers.dev` 这一段。Cloudflare 账号必须先注册它，否则不能部署。

**部署（Deploy）**：把你的代码推上云端。**改完绑定或密钥必须重新部署才生效**——这是超高频的踩坑点。

**API Token**：一串带"权限范围"的密钥，代替账号密码给程序用。能精确到"只能改 D1，不能碰别的"。

### 工具

**Node.js / npm / pnpm**：JavaScript 的运行环境和包管理器（相当于手机的应用商店）。

**Wrangler**：Cloudflare 官方命令行工具，用来部署、建库、看日志。

**esbuild**：打包工具，把源码压成一个文件再上传。

**wrangler tail**：实时查看线上后端的日志，是排查线上问题最快的办法。

### 攻击与防护

**XSS（跨站脚本）**：把恶意脚本塞进评论区，让别人的浏览器执行。防护办法：渲染时一律用 `textContent` 而不是 `innerHTML`。

**SQL 注入**：把 SQL 语句塞进输入框。防护办法：用 `?` 占位符绑定参数（本项目全程如此）。

**CSRF**：借用户的登录状态偷偷发请求。用 Bearer 令牌 + 不依赖 Cookie，天然规避。

**速率限制（Rate limit）**：本项目做了"同一人 10 秒内只能发一条"，防止刷屏。

## 七、一条评论的完整旅程

1. 访客点按钮 → 前端加载 Google 的脚本，弹出账号选择
2. 同意后 → Google 返回一张 **ID Token**
3. 前端把 token `POST` 到 `/login`
4. Worker 拉 Google 公钥 → **验章**
5. 逐项核对：`iss` 对不对、`aud` 是不是我、`exp` 过期没、邮箱验证过没
6. 全过 → 在 `users` 表里登记（用 `sub` 做主键，**不用邮箱**，因为邮箱会变）
7. 发一张 7 天的会话令牌给前端
8. 前端存进 `localStorage`，界面变成"头像 + 名字 + 评论框"
9. 发评论 → 带 `Bearer` 令牌 `POST /comments`
10. Worker 验令牌 → 查 10 秒冷却 → 写入 `comments` 表 → 返回成功
11. 前端重新拉列表 → 渲染（全程 `textContent` 转义）

## 十、可复用到下个项目的经验

1. **先问"这个东西能不能跑代码"**。静态托管只能发文件。
2. **凡是要"信"的判断，必须放服务端。** 前端的任何检查都只是体验优化。
3. **能自动化的验证，就不要靠肉眼。** 一个测试能省下无数次"再试一次"。
4. **报错要控制变量。** 设几个"应该成功"的对照组，剩下的那个变量就是原因。
5. **反复失败说明方案不适配**，不是运气不好。
6. **改完密钥/绑定一定要重新部署。** 忘了这一步会产生"代码明明对但就是不生效"的玄学。
7. **跨站登录不要用 Cookie。**
8. **永远检查 `aud`。** 这是 JWT 最经典的漏洞。
